# 🍰 Shop Service

> Асинхронный REST API для оформления и управления заказами кондитерского магазина.

Сервис предоставляет каталог начинок, декора и рецептов, расчёт стоимости изделий, оформление заказов, проверку доступности дат самовывоза и административное управление заказами.

## ✨ Возможности

- Просмотр активных начинок, декора и рецептов.
- Создание, обновление и мягкое удаление рецептов администратором.
- Предварительный расчёт стоимости изделия.
- Создание заказа с повторной серверной проверкой цены.
- Проверка свободных дат самовывоза и дневного лимита.
- Просмотр заказов текущего пользователя.
- Административный список заказов с фильтрацией, поиском и пагинацией.
- Получение подробной информации о заказе и изменение его статуса.
- Сводная информация для административного дашборда.

## 🧱 Архитектура

Проект разделён на слои по принципам Clean Architecture / Layered Architecture.

```text
Presentation (FastAPI endpoints, Pydantic schemas)
                     |
                     v
Application (Use cases, DTOs, repository interfaces)
                     |
                     v
Domain (business rules, enums, domain services)
                     ^
                     |
Infrastructure (SQLAlchemy, PostgreSQL, repositories, JWT, Redis)
```

### Presentation — `src/presentation/`

HTTP-слой приложения:
- регистрирует маршруты FastAPI;
- валидирует запросы через Pydantic;
- подключает зависимости авторизации и репозиториев;
- вызывает соответствующие use cases;
- определяет схемы входных и выходных данных.

### Application — `src/application/`

Содержит прикладные сценарии (`use_cases`), DTO и протоколы репозиториев (`interfaces`). Use case координирует операцию, но не привязывает бизнес-сценарий напрямую к HTTP или SQLAlchemy.

Основные сценарии: `AddOrder`, `CalculateTotalPrice`, `GetAvailability`, `ListOrders`, `GetDashboardSummary`, `UpdateOrderStatus`, операции с рецептами.

### Domain — `src/domain/`

Содержит бизнес-правила и понятия:
- `OrderStatus`;
- расчёт стоимости `calculate_total_price()`;
- вычисление самой ранней даты самовывоза `earliest_pickup_date()`;
- бизнес-константы и базовое доменное исключение.

### Infrastructure — `src/infrastructure/`

Технические реализации:
- SQLAlchemy-модели и асинхронная работа с PostgreSQL;
- сессии и репозитории;
- проверка JWT;
- клиент Redis.

### Пример потока создания заказа

1. Клиент отправляет `POST /v1/orders`.
2. FastAPI валидирует тело через `OrderAdd`.
3. Dependency извлекает UUID пользователя из access token.
4. Endpoint формирует `CreateOrderDTO`.
5. `AddOrder` проверяет дату и дневной лимит.
6. Загружает актуальные цены выбранного рецепта либо начинки и декора.
7. Самостоятельно рассчитывает стоимость и сравнивает её с `expected_price`.
8. При совпадении создаёт заказ со статусом `new`.
9. Результат преобразуется в DTO и возвращается клиенту.

## 🚀 Запуск

### Требования

- Python 3.13+;
- Poetry 2.x;
- PostgreSQL;
- Docker и Docker Compose (для контейнерного запуска).

### Локальный запуск

```bash
cd shop_service
poetry install
```

Создайте `.env` с необходимыми настройками (см. раздел «Конфигурация»), затем примените миграции:

```bash
poetry run alembic upgrade head
```

Запуск приложения из корня проекта:

```bash
PYTHONPATH=src poetry run python src/main.py
```

Либо через Uvicorn:

```bash
cd src
poetry run uvicorn main:app --reload
```

По умолчанию приложение слушает `0.0.0.0:8000`.

### Docker Compose

```bash
docker compose up --build
```

В текущем `docker-compose.yaml`:
- API внутри контейнера слушает `8000`, внешний порт — `8006`;
- PostgreSQL доступен с хоста на `127.0.0.1:5437`;
- данные БД хранятся в volume `app_db`;
- приложение ожидает успешный healthcheck PostgreSQL.

После запуска API доступно на `http://localhost:8006`.

> Миграции Alembic в Compose автоматически не запускаются — примените их отдельно. Compose использует `.env.docker` для контейнера приложения; переменные `PG_NAME`, `PG_USER`, `PG_PASS` используются для настройки контейнера PostgreSQL.

## 🔐 Авторизация

Access token передаётся в cookie:

```text
access_token
```

`get_access_token()` возвращает `401`, если cookie отсутствует. `check_access_token()` проверяет подпись публичным ключом, алгоритм (по умолчанию `RS256`), обязательные claims `exp` и `sub`, а также `token_type == "access"`.

`get_current_user_id()` преобразует `sub` в UUID. `get_current_admin_id()` дополнительно проверяет:

```json
{ "role": "admin" }
```

При другой роли возвращается `403 Forbidden`.

## ❤️ Healthcheck

### `GET /v1/healthcheck`

Проверка доступности API. Авторизация не требуется.

**Ответ `200 OK`:**

```json
{ "message": "success" }
```

## 🥧 Начинки

### `GET /v1/fillings`

Возвращает список активных начинок. Авторизация не требуется.

**Ответ `200 OK`:**

```json
[
  {
    "id": "UUID",
    "name": "Chocolate",
    "price_per_kg": 1200
  }
]
```

**Логика:** `GetFillings` получает через `ActiveRepository` только записи с `is_active = true`, сортирует их по `price_per_kg`, затем по `name`, и преобразует в `FillingDTO`.

`price_per_kg` — стоимость начинки за килограмм.

## 🎨 Декор

### `GET /v1/decorations`

Возвращает активные варианты декора. Авторизация не требуется.

**Ответ `200 OK`:**

```json
[
  {
    "id": "UUID",
    "name": "Chocolate decoration",
    "price": 300
  }
]
```

**Логика:** `GetDecorations` выбирает активные записи, сортирует по `price`, затем по `name`, и возвращает `DecorationDTO`. Цена декора добавляется к стоимости варианта с начинкой, если передан `decoration_id`.

## 🍰 Рецепты

### `GET /v1/recipes`

Список активных рецептов. Авторизация не требуется.

**Ответ `200 OK`:**

```json
[
  {
    "id": "UUID",
    "name": "Classic cake",
    "description": "Cake description",
    "price": "1500.00",
    "image_url": "https://example.com/image.jpg"
  }
]
```

**Логика:** выбираются активные рецепты, сортировка — `created_at` по убыванию (сначала новые).

### `GET /v1/recipes/{recipe_id}`

Получение активного рецепта по UUID. Авторизация не требуется.

**Ответ `200 OK`:** объект рецепта с полями `id`, `name`, `description`, `price`, `image_url`.

Если рецепт отсутствует или неактивен — `404 Not Found`.

### `POST /v1/recipes`

Создание рецепта. Требуется администратор.

**Тело запроса:**

```json
{
  "name": "Classic cake",
  "description": "Cake description",
  "price": "1500.00",
  "image_url": "https://example.com/image.jpg"
}
```

Валидация:
- `name`: 1–100 символов;
- `description`: непустая строка;
- `price`: больше 0, до 10 цифр и 2 знаков после запятой;
- `image_url`: до 500 символов.

**Ответ:** `201 Created`, созданный объект рецепта.

**Логика:** `CreateRecipe` передаёт валидированные данные репозиторию, который создаёт запись и выполняет `flush`. Имя рецепта уникально на уровне БД.

### `PATCH /v1/recipes/{recipe_id}`

Частичное обновление рецепта. Требуется администратор.

Можно передать любое непустое подмножество полей:

```json
{
  "price": "1700.00",
  "description": "Updated description"
}
```

Доступные поля: `name`, `description`, `price`, `image_url`.

**Логика:** используется `model_dump(exclude_unset=True)`, поэтому отсутствующие поля не перезаписываются значениями по умолчанию. Use case получает рецепт через `get_or_raise`, применяет переданные изменения и возвращает DTO. Если тело не содержит изменений, возвращается текущая запись.

> Особенность реализации: в отличие от публичного получения рецепта, обновление использует `get_or_raise`, а не `get_active_by_id`. Поэтому существующий неактивный рецепт также можно обновить.

### `DELETE /v1/recipes/{recipe_id}`

Мягкое удаление рецепта. Требуется администратор.

**Ответ:** `204 No Content`.

**Логика:** `DeleteRecipe` получает активный рецепт и обновляет `is_active` на `false`. Физически запись из БД не удаляется. После этого рецепт исчезает из публичного каталога. Отсутствующий или уже неактивный рецепт приводит к `404`.

## 💰 Расчёт стоимости

### `POST /v1/orders/total_price`

Предварительный расчёт цены до оформления заказа. Авторизация не требуется.

**Вариант с начинкой:**

```json
{
  "filling_id": "UUID",
  "decoration_id": "UUID",
  "weight_kg": "2.00"
}
```

**Вариант с рецептом:**

```json
{
  "recipe_id": "UUID",
  "weight_kg": "2.00"
}
```

`decoration_id` при выборе начинки необязателен.

**Ответ `200 OK`:**

```json
{ "total_price": "2700.00" }
```

Ограничение веса: от 1 до 10 кг включительно, не более двух знаков после запятой.

### Формулы

Для начинки:

\[
TotalPrice = Weight \times FillingPricePerKg + DecorationPrice
\]

Если декор не выбран, `DecorationPrice = 0`.

Для рецепта:

\[
TotalPrice = Weight \times RecipePrice
\]

Итог округляется до двух знаков после запятой через `Decimal.quantize(Decimal("0.01"))`.

### Правило выбора

`CakeSelection` обеспечивает взаимоисключающий выбор:
- если задан `recipe_id`, `filling_id` и `decoration_id` должны отсутствовать;
- если `recipe_id` не задан, обязателен `filling_id`;
- `decoration_id` можно указать только вместе с начинкой.

Выбранные справочные записи загружаются через `get_active_by_id`: неактивная или отсутствующая запись считается не найденной.

## 📅 Доступность дат

### `GET /v1/orders/availability`

Возвращает доступность каждой даты в диапазоне. Авторизация не требуется.

**Query-параметры:**

| Параметр | Тип | Обязательный |
|---|---|---|
| `date_from` | `date` | Да |
| `date_to` | `date` | Да |

Пример:

```http
GET /v1/orders/availability?date_from=2026-11-20&date_to=2026-11-30
```

**Ответ `200 OK`:**

```json
[
  {
    "day": "2026-11-20",
    "is_available": true,
    "free_slots": 2
  },
  {
    "day": "2026-11-21",
    "is_available": false,
    "free_slots": 0
  }
]
```

### Ограничения календаря

| Константа | Значение | Назначение |
|---|---:|---|
| `MAX_ORDERS_PER_DAY` | `3` | Максимум заказов на дату |
| `MAX_CALENDAR_RANGE_DAYS` | `62` | Максимальная разница между датами |
| `MIN_DAYS_BEFORE_PICKUP` | `1` | Минимальный срок до самовывоза |
| `SHOP_TIMEZONE` | `Europe/Minsk` | Часовой пояс магазина |

**Алгоритм `GetAvailability`:**

1. Проверяет, что `date_from <= date_to`.
2. Проверяет, что разница между датами не больше 62 дней.
3. Получает число заказов на каждую дату; `cancelled` не учитываются.
4. Вычисляет минимально допустимую дату самовывоза.
5. Для каждой даты вычисляет число свободных слотов.

\[
FreeSlots = \max(0, 3 - BookedOrders)
\]

Для даты раньше минимально допустимой `free_slots = 0`. `is_available` равен `true`, если свободных слотов больше нуля.

Диапазон с разницей ровно 62 дня допустим и содержит 63 календарные даты включительно. Некорректный или слишком большой диапазон приводит к `422 Unprocessable Entity`.

> Календарь показывает доступность, но при создании заказа проверка дневного лимита выполняется повторно.

## 🛒 Заказы пользователя

### `POST /v1/orders`

Создание заказа. Требуется действительный access token пользователя.

`user_id` берётся из JWT (`sub`), а не из тела запроса.

**Пример с начинкой:**

```json
{
  "customer_name": "John",
  "phone": "+123456789",
  "pickup_date": "2026-11-25",
  "weight_kg": "2.00",
  "recipe_id": null,
  "filling_id": "UUID",
  "decoration_id": "UUID",
  "inscription": "Happy Birthday",
  "expected_price": "2700.00"
}
```

**Пример с рецептом:**

```json
{
  "customer_name": "John",
  "phone": "+123456789",
  "pickup_date": "2026-11-25",
  "weight_kg": "2.00",
  "recipe_id": "UUID",
  "filling_id": null,
  "decoration_id": null,
  "inscription": null,
  "expected_price": "3000.00"
}
```

Ограничения полей:
- `customer_name` — максимум 100 символов;
- `phone` — максимум 20 символов;
- `inscription` — `null` или максимум 100 символов;
- `weight_kg` — от 1 до 10, два десятичных знака;
- `expected_price` — строго больше нуля, до 10 цифр и 2 знаков после запятой;
- идентификаторы — UUID.

**Ответ `200 OK`:** объект `OrderRead`, содержащий данные заказа, `id`, `number`, `status`, `total_price` и `created_at`. Схема также включает поля выбора (`recipe_id`, `filling_id`, `decoration_id`) и данные клиента.

### Подробный алгоритм `AddOrder`

1. **Проверка даты.** `earliest_pickup_date()` берёт текущую дату в `Europe/Minsk` и прибавляет один день. Более ранняя дата приводит к `PickupDateTooSoonError`.
2. **Проверка дневного лимита.** Репозиторий считает неотменённые заказы на выбранную дату. Если их уже три или больше, возникает `DayFullError`.
3. **Получение цены.** При `recipe_id` загружается активный рецепт и используется `recipe.price`. Иначе загружается активная начинка и, если указан `decoration_id`, активный декор.
4. **Пересчёт.** Сервер рассчитывает стоимость по актуальным значениям из БД.
5. **Сверка цены.** Рассчитанный `Decimal` сравнивается с `expected_price`. При несовпадении возникает `PriceMismatchError`, заказ не создаётся.
6. **Создание.** Из DTO удаляется `expected_price`; в данные добавляются `status=NEW` и рассчитанный `total_price`.
7. **Ответ.** Созданная модель преобразуется в `OutputOrderDTO`.

Проверка цены защищает от оформления заказа по устаревшей цене, показанной клиенту до изменения стоимости в каталоге.

### `GET /v1/orders/me`

Возвращает заказы текущего пользователя. Требуется access token.

**Ответ `200 OK`:** массив объектов `OrderRead`.

**Логика:** `ListMyOrders` вызывает `orders_by_user(user_id)`. Репозиторий выбирает только записи с данным `user_id`, сортируя по `created_at` от новых к старым. Идентификатор пользователя извлекается из токена.

## 🧑‍💼 Административное управление заказами

### `GET /v1/orders`

Список заказов для административной панели. Требуется администратор.

**Query-параметры:**

| Параметр | Тип | По умолчанию | Ограничения |
|---|---|---|---|
| `status` | список `OrderStatus` | Все статусы | Можно передать несколько |
| `search` | string | — | Поиск по имени, телефону, номеру |
| `limit` | int | `200` | 1–500 |
| `offset` | int | `0` | Не меньше 0 |

Пример:

```http
GET /v1/orders?status=new&status=confirmed&limit=50&offset=0
```

Поиск:

```http
GET /v1/orders?search=John
```

**Ответ `200 OK`:**

```json
{
  "total": 1,
  "items": [
    {
      "id": "UUID",
      "number": 1,
      "customer_name": "John",
      "recipe_name": null,
      "filling_name": "Chocolate",
      "pickup_date": "2026-11-25",
      "status": "new"
    }
  ]
}
```

**Логика `ListOrders`:**
- если статусы не переданы, выбираются все значения enum;
- имя клиента ищется через `ILIKE` с частичным совпадением;
- из строки поиска извлекаются цифры, по ним выполняется поиск телефона;
- если вся строка поиска состоит из цифр, дополнительно ищется точный `number`;
- к заказам присоединяются названия начинки и рецепта через `LEFT OUTER JOIN`;
- сортировка: `pickup_date` по возрастанию, `number` по убыванию;
- применяются `limit` и `offset`.

`total` — общее количество совпадений по фильтрам до пагинации.

### `GET /v1/orders/{order_id}`

Подробная информация о заказе. Требуется администратор.

Path-параметр: `order_id` — UUID заказа.

**Ответ `200 OK`:** объект `OrderDetailRead` с полями:
- `id`, `number`;
- `customer_name`, `phone`;
- `filling_name`, `recipe_name`, `decoration_name`;
- `weight_kg`, `inscription`, `total_price`;
- `pickup_date`, `status`, `created_at`.

**Логика:** репозиторий получает заказ по UUID и через `LEFT OUTER JOIN` извлекает названия начинки, рецепта и декора. Если запись не найдена, `GetOrderDetail` выбрасывает `NotFoundError` (`404`). Названия выбранных компонентов могут быть `null` в зависимости от типа заказа.

### `PATCH /v1/orders/{order_id}/status`

Изменение статуса заказа. Требуется администратор.

**Тело запроса:**

```json
{ "status": "confirmed" }
```

Допустимые значения: `new`, `confirmed`, `ready`, `done`, `cancelled`.

**Ответ `200 OK`:**

```json
{
  "id": "UUID",
  "status": "confirmed"
}
```

**Логика:** `UpdateOrderStatus` получает заказ через `get_or_raise`, обновляет поле `status` и возвращает `OrderStatusDTO`. Если заказ не найден — `404`.

Отдельных ограничений допустимых переходов между статусами сейчас нет: use case принимает любое допустимое значение enum.

## 📊 Дашборд

### `GET /v1/dashboard/summary`

Сводка административной панели. Требуется администратор.

**Ответ `200 OK`:**

```json
{
  "day": "2026-11-19",
  "new_orders_count": 5,
  "revenue": "7500.00",
  "unconfirmed_count": 3,
  "unconfirmed": [
    {
      "id": "UUID",
      "number": 10,
      "customer_name": "John",
      "recipe_name": null,
      "filling_name": "Chocolate",
      "pickup_date": "2026-11-22"
    }
  ]
}
```

`GetDashboardSummary` использует текущую дату в `Europe/Minsk` и формирует четыре показателя:

1. **`day`** — текущая дата магазина.
2. **`new_orders_count`** — число заказов, созданных сегодня (`created_at` от начала дня включительно до начала следующего дня исключительно); отменённые заказы исключаются.
3. **`revenue`** — сумма `total_price` заказов с `pickup_date` сегодня и статусом `done`.
4. **`unconfirmed_count` и `unconfirmed`** — количество и список заказов со статусом `new`.

Важно: количество новых заказов считается по дате создания, а выручка — по дате самовывоза. Это разные временные критерии.

## 🧠 Бизнес-логика

### Два способа выбрать изделие

| Вариант | Обязательное поле | Дополнительное поле |
|---|---|---|
| Через начинку | `filling_id` | `decoration_id` |
| Через рецепт | `recipe_id` | Нет |

Варианты взаимоисключающие. Это проверяется Pydantic-валидатором `CakeSelection` и ограничением `CHECK` таблицы `orders`.

### Цена и защита от устаревшей суммы

Клиент предварительно запрашивает цену через `/orders/total_price`. При оформлении сервер заново получает цены из БД, пересчитывает итог и сравнивает с `expected_price`. При расхождении возвращается конфликт, и заказ не создаётся.

### Лимит заказов

На одну дату допускается максимум 3 неотменённых заказа. Учитываются статусы `new`, `confirmed`, `ready`, `done`; `cancelled` не занимает слот.

### Минимальный срок

Самовывоз доступен начиная со следующего дня по календарю `Europe/Minsk`. Правило применяется как в календаре, так и при создании заказа.

### Soft delete рецептов

Рецепт не удаляется физически: `is_active` переключается на `false`. Публичные методы каталога возвращают только активные записи.

### Номер заказа

`Order.number` генерируется средствами БД через `Identity` и имеет уникальное ограничение. Он существует наряду с UUID `Order.id`.

### Транзакции

`get_session()` открывает асинхронную SQLAlchemy-сессию:
- после успешного выполнения запроса — `commit`;
- при исключении — `rollback`;
- после завершения контекста сессия закрывается.

Репозитории используют `flush()` внутри текущей транзакции; окончательный commit выполняет dependency сессии.

## 📦 Модели данных

В проекте четыре основные SQLAlchemy-модели.

### `Order` — заказ

| Поле | Назначение |
|---|---|
| `id` | UUID primary key |
| `user_id` | UUID пользователя, индекс |
| `number` | Уникальный числовой номер, `Identity` |
| `customer_name` | Имя клиента, до 100 символов |
| `phone` | Телефон, до 20 символов |
| `filling_id` | FK на `fillings.id`, nullable |
| `recipe_id` | FK на `recipes.id`, nullable |
| `decoration_id` | FK на `decorations.id`, nullable |
| `weight_kg` | `Numeric(4, 2)` |
| `total_price` | `Numeric(10, 2)` |
| `pickup_date` | Дата самовывоза, индекс |
| `inscription` | Необязательная надпись, до 100 символов |
| `status` | Enum `OrderStatus` |
| `created_at`, `updated_at` | Временные метки |

Ограничение `CHECK` допускает только:
- `recipe_id IS NOT NULL`, `filling_id IS NULL`, `decoration_id IS NULL`; либо
- `recipe_id IS NULL`, `filling_id IS NOT NULL`.

### `Filling` — начинка

`id`, уникальное `name` (до 100 символов), `price_per_kg`, `is_active`, `created_at`, `updated_at`.

### `Decoration` — декор

`id`, уникальное `name` (до 100 символов), `price`, `is_active`, `created_at`, `updated_at`.

### `Recipe` — рецепт

`id`, уникальное `name` (до 100 символов), `description`, `price` (`Numeric(10, 2)`), `image_url` (до 500 символов), `is_active`, `created_at`, `updated_at`.

### Общие mixins

- `IdPkMixin` — генерация UUIDv7;
- `CreatedAtMixin` — дата создания;
- `UpdatedAtMixin` — дата обновления;
- `IsActiveMixin` — признак активности;
- `NameMixin` — уникальное имя длиной до 100 символов.

## 🚦 Статусы заказа

Enum `OrderStatus` (`src/domain/enums/order_status.py`):

| Статус | Значение | Смысл |
|---|---|---|
| Новый | `new` | Заказ создан, ожидает обработки |
| Подтверждён | `confirmed` | Заказ подтверждён |
| Готов | `ready` | Заказ готов к выдаче |
| Выполнен | `done` | Заказ завершён |
| Отменён | `cancelled` | Заказ отменён |

Новый заказ получает статус `new`. Изменение статуса доступно администратору через `PATCH /orders/{order_id}/status`. Отдельная state machine переходов не реализована.

## ⚠️ Обработка ошибок

Прикладные исключения наследуются от `AppError` и централизованно преобразуются в HTTP-ответы в `register_exception_handlers()`.

| Исключение | HTTP | Значение |
|---|---:|---|
| `TokenValidationError` | 401 | Недействительный токен |
| `InvalidTokenTypeError` | 401 | Токен не является access token |
| `NotFoundError` | 404 | Ресурс не найден |
| `IntegrityConstraintError` | 409 | Нарушено ограничение БД |
| `PriceMismatchError` | 409 | Цена изменилась |
| `DayFullError` | 409 | Дата заполнена |
| `PickupDateTooSoonError` | 422 | Слишком ранняя дата самовывоза |
| `InvalidDateRangeError` | 422 | Некорректный диапазон дат |
| `DatabaseError` | 500 | Ошибка БД |

Формат прикладной ошибки:

```json
{
  "detail": "Error message"
}
```

Ошибки валидации FastAPI/Pydantic обрабатываются стандартным механизмом FastAPI.

## 🔎 Особенности текущей реализации

Ниже перечислены важные детали, непосредственно следующие из исходного кода:

1. **Авторизация через cookie.** Токен читается из `access_token`, а не из `Authorization: Bearer`.
2. **Выпуск JWT не реализован в представленном API.** Есть только проверка токена и извлечение пользователя/роли.
3. **Redis-клиент создаётся при импорте.** В текущих use cases и endpoints активного использования Redis не обнаружено; при завершении приложения клиент закрывается.
4. **Kafka-модуль пуст.** В `infrastructure/messaging/kafka.py` нет реализации обмена сообщениями.
5. **Тестовая директория не содержит тестовых сценариев** — в архиве присутствует только `tests/__init__.py`.
6. **Переходы статусов отдельно не ограничены.** Администратор может установить любое допустимое значение `OrderStatus`.
7. **Проверка дневного лимита не резервирует слот атомарно.** Проверка количества и создание заказа — отдельные операции; при конкурентных запросах теоретически возможна гонка.
8. **Цена сверяется точным сравнением Decimal.** Допуск на расхождение не предусмотрен.
9. **`recipe.price` умножается на вес.** Несмотря на название поля `price`, в расчёте оно используется как цена за килограмм.
10. **Удаление рецепта — soft delete.** Запись остаётся в БД с `is_active = false`.
11. **Поиск телефона использует цифры из поисковой строки.** Это позволяет искать номер без привязки к форматированию.
12. **Показатели дашборда используют разные даты.** Новые заказы считаются по `created_at`, выручка — по `pickup_date` и статусу `done`.
13. **Compose не запускает миграции автоматически.** PostgreSQL healthcheck контролирует готовность контейнера БД, но не применяет схему.
